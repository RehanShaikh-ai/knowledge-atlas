# v0.2.2 infrastructure design

## Scope

This design implements Workstream B of the v0.2.2 contract: additive PostgreSQL
schema, migration validation, Compose compatibility, and integration coverage. API
and ORM implementation remain owned by Workstream C.

## Schema plan

Migration `0003` follows `0002`. It adds nullable `notes.metadata` (`JSONB`) and
creates `sources`. Source provenance is workspace-scoped, uniquely identified by
`(workspace_id, source_identifier)`, and has the three contract indexes:

- `idx_sources_workspace_identifier` (unique)
- `idx_sources_workspace_batch`
- `idx_sources_note_id`

Foreign keys are deliberately asymmetric: deleting a workspace cascades to its
sources; deleting a note retains the source and sets `sources.note_id` to `NULL`.
The migration also constrains the canonical source and import-status enumerations.

## Compatibility and rollback

The migration neither changes nor rebuilds pre-existing tables. Existing notes get
`NULL` metadata. Downgrade drops `sources` and then the additive note column, leaving
the v0.2.1 schema and its data unchanged.

## Validation

Run `uv run python scripts/verify_migrations.py` to enforce one Alembic head at
revision `0003`, `uv run pytest tests/integration -v` for PostgreSQL/Testcontainers
coverage, and `docker compose config --quiet` for Compose syntax. The Testcontainers
suite runs migrations against PostgreSQL 16, never a mocked database.

## Integration risk

The existing `notes.search_vector` generated-column model mapping must remain aligned
with migration `0002`; otherwise normal note creation fails in PostgreSQL. That model
is Workstream C-owned and is tracked as an integration dependency rather than worked
around in infrastructure tests.
