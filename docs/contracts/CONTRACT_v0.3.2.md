# 0. Cross-Workstream Conflict Prevention Protocol

**Read this section first. It exists because of recurring conflicts between Workstream B (Backend) and Workstream C (Infrastructure) in v0.3 sprints. It applies to every workstream, but the primary mechanism targets the Backend–Infrastructure boundary.**

## 0.1 The Schema Handoff Gate

Workstream C must not write a single line of Alembic migration for this release until Workstream B has:

1. Finalized all SQLAlchemy model files listed in §6.1
2. Updated `backend/app/models/__init__.py` to import every new model
3. Opened a PR titled exactly `schema-handoff/v0.3.2` containing only those model files and `__init__.py` — no routes, no services, no schemas
4. That PR is approved (one approval from any contributor) and merged to `main`

**Workstream C's migration PR cannot be opened until the schema-handoff PR is merged.**

This is the enforcement mechanism: the migration is generated by running `uv run alembic revision --autogenerate` against the merged models. If Workstream B changes a model after the handoff PR is merged, they must open a second `schema-handoff/v0.3.2-patch-N` PR and Workstream C regenerates the affected migration. There is no silent in-place model editing after handoff.

## 0.2 The Compose Lock

`docker-compose.yml` is a conflict magnet. For this release:

- Any change to `docker-compose.yml` requires the author to post a **Compose Change Notice** as a comment on the `main` branch's latest commit (or as a pinned PR comment) **before opening their branch**.
- The notice states: which service is being added/modified, what new ports or volumes are involved, and which other workstream (if any) needs to know.
- No Compose PR may be merged if another Compose PR is currently open. One at a time.
- Workstream C owns Compose; Workstream B must file a Compose Change Notice (not open a PR) if their backend changes require a new Compose service or env var.

## 0.3 Environment Variable Handoff

- Workstream B must add any new env var it uses to `backend/app/core/config.py` **and** immediately open a PR against `.env.example` (owned by Workstream C) as a joint PR or as a separate tiny PR that Workstream C merges first.
- No backend code may reference an env var not yet present in `.env.example` on `main`.
- Workstream C must not add an env var to `.env.example` that Workstream B hasn't requested in writing (PR comment or the env-var section of this contract, §15).

## 0.4 `models/__init__.py` is Backend's Responsibility, Always

Every new SQLAlchemy model introduced by Workstream B must be imported in `backend/app/models/__init__.py` **in the same commit as the model file**. Workstream C must verify this before running autogenerate. If `__init__.py` is missing an import, Workstream C files a bug against Workstream B — they do not work around it by editing the file themselves.

## 0.5 Integration Branch Creation

The integration branch (`review/v0.3.2-integration`) is created by Workstream C only after:
- The schema-handoff PR is merged
- The Compose additions PR is merged
- All three workstream branches have passing CI on their individual branches

Merging order into the integration branch is fixed: `infra` → `backend` → `frontend`. This order is not negotiable — it ensures the database exists before backend tests run and the API exists before frontend integration tests run.

# 1. Objective

v0.3.2 introduces the Knowledge Graph engine — the capability that elevates Knowledge Atlas from a semantic notes tool into a genuine knowledge system.

This release adds:

- **A structured graph of entities and concepts** extracted from notes
- **Automatic entity and relationship extraction** via local LLM
- **Automatic note-to-note link suggestions** based on extracted entities
- **GraphRAG** — multi-hop graph traversal combined with vector retrieval
- **Hybrid graph + vector retrieval** as a unified retrieval mode
- **Constellation visualization** — interactive graph of notes, entities, relationships
- **Automatic clustering** of related concepts
- **Graph-aware assistant** that reasons over relationships and paths
- **Knowledge Explorer** — deep-dive into any entity
- **Manual graph editing** — create, edit, delete entities and relationships
- **Accept/Reject AI link suggestions** flow
- **Graph indexing pipeline** (extract/update on note save)
- **Graph re-indexing** for model/logic changes
- **Graph job status and failure handling**
- **Relationship provenance** — which chunk caused a relationship
- **Graph search and highlighting**
- **Graph filters** by entity type, relationship, cluster, note

This release does not implement authentication, authorization, real-time collaboration, billing, production deployment, or any feature listed in §2.2.

## 6.8 Migration Requirements

A single Alembic revision creates all six tables plus the indexes above. The migration must:

- Not be written until the schema-handoff PR is merged (§0.1)

- Include all indexes from §6.7

# 7. Qdrant Payload Extension

No new Qdrant collections are introduced. The existing per-workspace collections gain two additional payload fields on new or re-indexed chunks:

```json
{
  "entity_ids": ["entity-uuid-1", "entity-uuid-2"],
  "cluster_id": "cluster-uuid-or-null"
}
```

Old chunks without these fields are treated as `entity_ids: []`, `cluster_id: null` — the search and filter code must handle absent payload keys gracefully (never crash on missing field).

These fields are populated by `graph_index_service.index_note_graph()` after entity extraction completes. They are not populated at chunk-creation time — chunk indexing and graph indexing are separate pipeline steps.

# 8. Entity and Relationship Extraction Contract

## 8.1 Extraction Pipeline

```text
Note saved or updated
        │
        ▼
extract_entities_job (ARQ)
        │
        ▼
entity_extraction_service.extract_entities_for_note
  → LLM call (Ollama, structured output)
  → Upsert GraphEntity rows (dedup by name within workspace)
  → Create EntityChunk provenance rows
        │
        ▼
extract_relationships_job (ARQ) — triggered after entity job completes
        │
        ▼
relationship_extraction_service.extract_relationships
  → LLM call for pairs of entities in the same note/chunk
  → Upsert GraphRelationship rows
  → Create EntityChunk provenance rows for relationships
        │
        ▼
generate_link_suggestions (link_suggestion_service)
  → Compare shared entity sets across notes in workspace
  → Upsert LinkSuggestion rows (status = "pending")
        │
        ▼
graph_index_service.index_note_graph
  → Update Qdrant chunk payloads with entity_ids and cluster_id
```

## 8.2 LLM Extraction Format

The extraction prompt must request structured JSON output. The LLM response is parsed with Pydantic validation — if the model returns malformed JSON, the job fails with a sanitized error (no raw LLM output in `index_jobs.error_message`).

Entities output format:

```json
{
  "entities": [
    { "name": "string", "type": "concept|person|technology|project|place|event|unknown", "description": "string" }
  ]
}
```

Relationships output format:

```json
{
  "relationships": [
    { "source": "entity name", "target": "entity name", "type": "string", "description": "string", "confidence": 0.85 }
  ]
}
```

Both `source` and `target` must match the canonical `name` of an entity already extracted from this note. Relationships referencing non-existent entity names are dropped, not created.

## 8.3 Entity Deduplication

Before creating a `GraphEntity` row, the service checks for an existing entity with the same `(workspace_id, name)` (case-insensitive comparison, then stored in the original casing of the first occurrence). On match:
- If `is_manual = True` on the existing row: do not overwrite `name`, `description`, or `entity_type` — only add provenance
- If `is_manual = False`: update `description` if the new extraction's confidence is higher

## 8.4 Re-indexing

Re-indexing (`reindex_workspace_graph`) rebuilds extraction from scratch:
- Deletes all AI-extracted entities (`is_manual = False`) for the workspace
- Deletes all AI-extracted relationships (`is_manual = False`)
- Deletes all provenance rows (`entity_chunks`) for the workspace
- Re-runs the extraction pipeline for every note in the workspace
- Does not delete manually-created entities or relationships (`is_manual = True`)

### Accept Suggestion

`POST /api/v1/suggestions/{suggestion_id}/accept`

Effect:
1. Creates a `note_links` row (v0.2.1 format) between `source_note_id` and `target_note_id`
2. Sets `suggestion.status = "accepted"`, `suggestion.decided_at = now()`
3. Returns the created `note_links` row

If a `note_links` row already exists between the two notes: sets suggestion to `accepted` without creating a duplicate link. Returns the existing link.

### Reject Suggestion

`POST /api/v1/suggestions/{suggestion_id}/reject`

Sets `status = "rejected"`, `decided_at = now()`. Returns the updated `LinkSuggestionResponse`. Does not delete the suggestion row — retained for history and to prevent re-suggesting the same pair.

# 10. GraphRAG Pipeline

```text
GraphRAGRequest (query + max_hops + context_limit)
        │
        ▼
vector_retrieval (semantic/hybrid — v0.3.1 retrieval_service)
        │
        ▼
traverse_graph (graph_rag_service.traverse_graph)
  → For each retrieved chunk's entity_ids, fetch connected entities up to max_hops
  → Collect traversed entities and the relationships used
        │
        ▼
assemble_graph_context (graph_rag_service.assemble_graph_context)
  → Combine retrieved chunk text + entity descriptions + relationship summaries
  → Bounded by CONTEXT_TOKEN_LIMIT (same env var as v0.3.1)
        │
        ▼
llm_service.generate (same provider abstraction as v0.3.1)
        │
        ▼
GraphRAGResponse (answer + citations + graph_context)
```

If no entities are associated with the retrieved chunks (e.g. graph has never been indexed), GraphRAG degrades gracefully to standard RAG with `graph_context.hops = 0` and empty traversal arrays. It does not fail.

# 11. Error Contract

All errors follow the existing `{ "error": { "code": "...", "message": "..." } }` shape.

New codes for v0.3.2:

| HTTP Status | Code | Trigger |
|---|---|---|
| 409 | `CONFLICT` | Duplicate entity name in workspace; duplicate relationship (same pair + type) |
| 404 | `ENTITY_NOT_FOUND` | Entity does not exist |
| 404 | `RELATIONSHIP_NOT_FOUND` | Relationship does not exist |
| 404 | `CLUSTER_NOT_FOUND` | Cluster does not exist |
| 404 | `SUGGESTION_NOT_FOUND` | Link suggestion does not exist |
| 422 | `VALIDATION_ERROR` | Invalid request, self-relationship, invalid entity type, `max_hops` > 2, empty graph search |
| 422 | `SUGGESTION_ALREADY_DECIDED` | Accept/reject on a non-pending suggestion |
| 500 | `EXTRACTION_FAILED` | LLM extraction job failed after max retries |
| 500 | `GRAPH_INDEX_ERROR` | Graph indexing error (Qdrant payload update failure) |

All prior error codes from v0.1.1–v0.3.1 remain valid and unchanged.

# 12. Extraction and Graph Indexing Pipeline Contract

## 12.1 Trigger on Note Save

When a note is created or updated via `POST /api/v1/workspaces/{workspace_id}/notes` or `PATCH /api/v1/notes/{note_id}`:

1. The note save completes and returns to the client (synchronous).
2. `extract_entities_job` is enqueued immediately after the note is saved.
3. `extract_relationships_job` is chained to run after `extract_entities_job` completes.
4. `link_suggestion_service.generate_link_suggestions` runs after relationships are extracted.

The HTTP response for the note save does not wait for extraction. The client polls via `GET /api/v1/jobs/{job_id}` if it wants extraction status.

## 12.2 Graph Re-indexing

`POST /api/v1/workspaces/{workspace_id}/graph/reindex` triggers `cluster_notes_job` on top of full re-extraction. The re-indexing job:

- Deletes only AI-extracted graph data (§8.4)
- Preserves manually-created entities and relationships (`is_manual = True`)
- Reports final counts in `IndexJob.error_message` on completion (e.g. "Extracted 42 entities, 78 relationships from 15 notes")

## 12.3 Job Failure Handling

- Each extraction job is retried up to `JOB_MAX_RETRIES` (from v0.3.1 env var)
- Sanitized error in `index_jobs.error_message` — no raw LLM output, no file paths, no stack traces
- `GET /api/v1/jobs/{job_id}` returns full failure detail
- `POST /api/v1/jobs/{job_id}/retry` re-enqueues — same as v0.3.1
